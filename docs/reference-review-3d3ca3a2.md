## 1. 优点清单

### A 组｜看门狗：六个判断，每个都在防一种具体的误杀

| # | 判断 | 代码 | 它在防什么 |
|---|---|---|---|
| A1 | 巡检挂在网关进程内，而不是 cron / 第二个守护进程 | `_watchdog_loop` 作为 daemon 线程 | 少一个「守护者自己也挂了」的失效面 |
| A2 | 两种故障形态用两把尺子 | `alive and 300s` vs `fails ≥ 3` | 端口在听≠死了，可能正在 prefill |
| A3 | 宽限期(150s) 必须 > 冷启动(75s) | `WD_GRACE_S`，且宽限期内**不计数** | 否则服务还在加载就被判死 → 自杀循环 |
| A4 | 有请求在飞时阈值翻倍 | `need = THRESHOLD * (2 if inflight else 1)` | 131k prefill 期间杀掉它等于自杀 |
| A5 | 重启只调 `start-flash.py`，不复刻命令行 | `_wd_restart()` | 命令行两处维护必然漂移 |
| A6 | 退避 + 稳定期才清零 + 快照脱敏 | `min(150·2^n, 1800)` / `STABLE=300` / `_wd_snapshot()` | 抖动期反复全速捅上游；`/health` 免鉴权 |

**A1 值得单独说**，因为它是唯一一条「理由部分错了、结论仍然对」的设计。
提交里写了三条理由：① 本机 launchd 完全不可用；② 网关是常驻进程；③ 巡检需要知道「有没有请求在飞」。
其中 ① 在 5 小时后被自己的 `ea6b503e` 推翻——**加 `sudo` 就成功了**，launchd 没坏，是执行上下文对该 GUI 域
没有「新增作业」权限，被 launchd 泛化成 `5: Input/output error`。
但结论依然成立：**理由 ③ 是不可替代的**——`_wd_inflight_total()` 读的是网关进程内的
`_model_inflight` 字典，任何外部脚本都看不到这个信息。这正是 A4（阈值翻倍）能存在的前提。
> 可复用教训：把守护放进业务进程，最硬的理由应该是「它需要只有我知道的状态」，而不是「我的 init 坏了」。

**A2 是最容易被抄错的一条**。两种故障用同一个计数器是常见写法，但它们的**证据强度不同**：

```python
if alive:                                        # 端口在听 = 可能在算
    if now - st["first_fail"] < WD_HUNG_TIMEOUT_S:  # 300s，用 first_fail 计时
        st["state"] = "degraded"; return
    reason = f"端口在监听但 {int(now - st['first_fail'])}s 无响应"
else:                                            # 端口无监听 = 确定死了
    if st["fails"] < need:                       # 3 次（或 6 次），用计数
        st["state"] = "down"; return
```

后果差异实测：进程崩溃 → **40~60s** 判死；端口在听但不回 → **≈305s**。若抄成统一 3 次，
卡死分支会在 60s 就重启一个正在做长 prefill 的服务。

**A6 的脱敏**常被忽略：`/health` 是免鉴权路径，快照里只给
`state / fails / restarts / last_check_ago_s / last_error / next_attempt_in_s`，
**不含**权重路径、端口来源、启动命令行。

### B 组｜两个 auto 硬约束：把「概率」变成「声明」

| # | 判断 | 代码 | 为什么这是对的 |
|---|---|---|---|
| B1 | 贵模型只在深度档参与，且是**硬约束** | `AUTO_DEEP_ONLY` + 候选池过滤 | 分差 0.03~0.05 扛不住负载波动，调权重改不了 |
| B2 | 摘空则**不生效**（fail-open） | `if gated and len(gated) != len(cands)` | 策略配错不能变成 502 |
| B3 | 参数量三级优先级：覆写 > 元数据 > 名字推断 | `_auto_param_b` 首行取 `MODEL_PARAM_OVERRIDES` | 换运行时后元数据消失，是**静默降级** |

**B1 的真正价值不是"省一个请求"，而是把一类决策从"打分"里摘出去。**
`balanced` 的 quality 因子按候选池内参数量对数归一，池里最大的模型**恒得 1.00**；
当大模型比小模型慢时（125B ~40 t/s vs 27B ~90 t/s），速度因子只能部分抵消。实测 A/B（`tests/test_auto_deep_only.py`）：

```
== 1. 未配置 ==            短问答 → big125b [tier=light]     ← 12.6s
== 2. TG_AUTO_DEEP_ONLY == 短问答 → mid27b   [tier=light]     ← 2.0s（6.3×）
== 3. 常规档 ==            2000 字符 → mid27b  [tier=standard]
== 4. 深度档不受限 ==      8000 字符 → big125b [tier=deep]
                           带工具   → big125b [tier=deep]
== 6. 摘空不生效 ==        唯一候选=125B → big125b            ← 不 503
```

一句「1+1」从 12.6s 变 2.0s，而且**深度档完全没被削弱**（长输入、带 tools 仍走 125B）。
这是「硬约束」相比「调 quality 权重」的本质差别：后者会同时压低它在深度档的分数。

**B3 修的是一个"静默降级"**，这类 bug 的特征是**不报错、只是慢慢变差**：
gmlx 的模型名 `qwen3.8-flash-next` 里没有数字、又没有 `/api/show` 元数据 → `_auto_param_b` 返回 `None`
→ `tier_fit` 与 `quality` 双双落到 0.35 中性低分 → **深度档不再选 125B 而退回 27B**。
三级优先级的写法（`override → meta → name`）比"改名字"或"改推断正则"都稳：
它把部署事实从**约定**变成了**配置**。解析器还刻意容错——坏项跳过、空串不抛异常：

```python
_k, _sep, _v = _item.partition("=")
if not _k or not _sep: continue
try:    MODEL_PARAM_OVERRIDES[_k] = float(_v)
except ValueError: continue
```

**C1 是这三个测试文件里最值得学的东西。** 25 条断言中没有一条是"`_wd_tick` 被调用了"，
全都在描述**可观测的行为**：


第二条尤其关键：`grace_fails` 是**为可观测性单独开的计数器**——不计入判死，但要让运维看见。

**C3 的价值在于"排除了才算查过"**。那份矩阵里每一行都是一个别人会重复尝试的动作，

省下的是别人的几小时，而不是自己的几分钟——这正是「可复用参考」和「个人笔记」的分界线。

### 🔴 D1｜退避序列实际失效（`healthy_since` 语义错位）　**[已修复 v2026.11.14.1]**

`healthy_since` 的语义是「自某次成功探测起」，却被当成「自上次重启起」用，而且**重启时不清零**：

```python
if not st["healthy_since"]:      # 只在 0 时写 → 长跑后再重启，它仍是几小时前的值
    st["healthy_since"] = now
if st["restarts"] and now - st["healthy_since"] >= WD_STABLE_RESET_S:
    st["restarts"] = 0           # 于是恢复后第一次健康就把退避清零
```

线上留痕（原始日志）：

```
[2026-11-11 16:36:58] 🚑 8090 不可用（连续 3 次探测失败），已拉起重启脚本
[2026-11-11 16:37:18] 🐕 8090 已稳定 149972s，重启退避计数归零   ← 20 秒后判「已稳定 41.6 小时」
```

真实端口起落复现：`① 150s → ② 恢复（restarts 归零）→ ③ 再判死仍是 150s`，设计应为 300s。
后果：只要「重启→恢复→又挂」，`300/600/1200/1800` 与封顶**永不生效**，抖动期变成每 150s 捅一次上游。
修法一行：判死时 `st["healthy_since"] = 0.0`。

### 🔴 D2｜健康检查硬依赖 `NO_PROXY=*`　**[已修复 v2026.11.14.1]**

`_wd_probe()` 用 `urllib.request.urlopen`，默认 opener 会读 `HTTP_PROXY`。子进程实测：

| 环境 | 一个**完全健康**的上游 |
|---|---|
| `HTTP_PROXY=http://127.0.0.1:1`（死代理） | 被判**不健康** |
| 同上 + `NO_PROXY=*` | 正常 |

当前 plist 有这一项所以没出事，但谁改 plist 时漏掉，代理一挂就变成「健康时的自杀循环」。
修法：`urllib.request.build_opener(urllib.request.ProxyHandler({}))`，别依赖环境变量。

## 3. 如果另一个 agent 要复用，改这 7 处

1. **`_wd_targets()`** 换成你的运行时端口来源（它读 `flash-runtime.json`，这是个很本机的约定）；
2. **`WD_GRACE_S`** 必须 > 你的冷启动时间，建议 2× 余量（本机 150 vs 75）；
3. **`_wd_probe()`** 加 `ProxyHandler({})`（见 D2）；
4. **判死处补 `healthy_since = 0.0`**（见 D1）；
5. **`_wd_restart()`** 的目标换成你的启动脚本，**不要**把命令行搬进来（A5 的意义就在这里）；
6. **`TG_AUTO_DEEP_ONLY`** 默认空集要保留，否则会改变既有人的行为；
7. **`TG_MODEL_PARAMS`** 键要写**上游真实模型名**（不是别名），别名在 `deep_only` 那条路径才解析。

## 4. 一句话结论

这个提交值得被当参考，**不是因为它写了多少行，而是因为它把「什么算故障」拆成了可判定的证据**：
端口无监听 → 3 次计数；端口在听 → 300s 计时；有在飞请求 → 阈值翻倍；宽限期内 → 只观察不计数。
四个维度互相独立、各自有测试、各自有日志文案。

它同时也是一份很好的「错误示范」补充材料：**结论对、理由错**（launchd）、
**语义对、生命周期错**（`healthy_since`）、**逻辑对、环境依赖错**（`NO_PROXY`）——
这三类恰好是"能跑起来、跑得还挺久、直到某天才炸"的经典形态。
